## Hard Genesis-Horizon rule

Inside the Genesis Horizon, Genesis is Genesis-native. CPU, RAM, registers, opcodes, binary addresses, buses, filesystems, operating systems and equivalent conventional-computing concepts must not be promoted to internal Genesis ontology merely because an implementation or donor package uses them. Treat existing ABI/ISA, implementation and donor artifacts as host/backend/transduction realizations unless authoritative Genesis mathematics explicitly establishes an internal realization. Preserve those artifacts; this integration does not delete or rewrite `language/`.

The [Horizon boundary](GENESIS_HORIZON.md), [four-object model](LAYER_ZERO_FOUR_OBJECT_MODEL.md) and [adjacent information path](LAYER_ZERO_INFORMATION_PATH.md) remain in force. No nonadjacent bypass is introduced. Earlier shell/address analogies describe working roles, not conventional host ontology inside Genesis.

The three-authority Genesis Trinity above is distinct from DP-001's Hardware / Software / Guardian architectural grouping and from Trinity 3.0 donor coordinates. No one grouping silently replaces another authority.
